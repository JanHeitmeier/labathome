ANFORDERUNGEN & CONSTRAINTS
================================================================================

Funktionale Anforderungen:
- Verschiedene physikalische Größen (Temperatur, Druck, Masse, Zeit, etc.)
- Einheiten-Conversion (z.B. Celsius ↔ Fahrenheit ↔ Kelvin)
- Typsichere Operationen (keine versehentliche Addition von Temperatur + Druck)
- Einfache API für Step-Implementierungen
- Serialisierung (JSON/Flatbuffers)

Fachliche Vorgaben (von Domain-Experte):
- uint16_t für die meisten Sensoren ausreichend
- Intern standardisierte SI-Einheiten
- Temperatur: Zehntel-Kelvin (Faktor 10)
- Druck: Kilopascal (da 65000 Pa schnell überschritten)
- Flexibilität bei Eingabe, Standardisierung intern

Embedded-Constraints:
- Begrenzte RAM (512 KB SRAM auf ESP32-S3, weniger auf anderen MCUs)
- Flash-Speicher limitiert (variiert je nach Plattform)
- Performance-kritisch (Echtzeit-Regelung)
- Geringe Code-Größe erwünscht (wichtig für ROM-limitierte MCUs)
- Portabilität zu verschiedenen Architekturen (32-bit, 16-bit MCUs)
- KIS-Prinzip (Keep It Simple)

================================================================================
METHODE 2: RUNTIME-TAGGED UNION (EINFACH)
================================================================================

Beschreibung:
- Lightweight Alternative zu std::variant
- Enum für Quantity-Typ + Union für Wert
- Runtime-Checks beim Zugriff

Code-Beispiel:
```cpp
enum class QuantityType : uint8_t {
    None, Temperature, Pressure, Mass, Percent
};

struct PhysicalValue {
    QuantityType type;
    uint16_t value;  // Intern standardisiert
    
    bool operator==(const PhysicalValue& other) const {
        return type == other.type && value == other.value;
    }
    
    PhysicalValue operator+(const PhysicalValue& other) const {
        assert(type == other.type);  // Runtime-Check!
        return {type, uint16_t(value + other.value)};
    }
};

// Factory-Funktionen:
PhysicalValue makeTemperature(float celsius) {
    return {QuantityType::Temperature, 
            uint16_t((celsius + 273.15f) * 10.0f)};
}

// Verwendung:
auto val = input->read();  // PhysicalValue
if (val.type == QuantityType::Temperature) {
    float celsius = (val.value / 10.0f) - 273.15f;
}
```

================================================================================
METHODE 3: STRONG TYPES MIT TEMPLATES (TYPSICHER)
================================================================================

Beschreibung:
- Separate Klassen für jede physikalische Größe
- Template-Basis für Code-Wiederverwendung
- Compile-Zeit-Sicherheit durch Typ-System

Code-Beispiel:
```cpp
// Template-Basis
template<typename Derived, typename StorageType = uint16_t>
class PhysicalQuantityBase {
protected:
    StorageType value_;
public:
    constexpr explicit PhysicalQuantityBase(StorageType val = 0) 
        : value_(val) {}
    
    constexpr StorageType raw() const { return value_; }
    
    // Operatoren nur für GLEICHEN Typ!
    constexpr bool operator==(const Derived& other) const {
        return value_ == static_cast<const PhysicalQuantityBase&>(other).value_;
    }
    
    constexpr Derived operator+(const Derived& other) const {
        return Derived::fromRaw(value_ + 
            static_cast<const PhysicalQuantityBase&>(other).value_);
    }
};

// Konkrete Implementierung
class Temperature : public PhysicalQuantityBase<Temperature, uint16_t> {
public:
    // Factory-Methoden
    static constexpr Temperature fromRaw(uint16_t raw) { 
        return Temperature(raw); 
    }
    static constexpr Temperature fromKelvin(float k) {
        return Temperature(uint16_t(k * 10.0f));
    }
    static constexpr Temperature fromCelsius(float c) {
        return fromKelvin(c + 273.15f);
    }
    static constexpr Temperature fromFahrenheit(float f) {
        return fromKelvin((f - 32.0f) * 5.0f / 9.0f + 273.15f);
    }
    
    // Conversion zurück
    constexpr float toKelvin() const { return value_ / 10.0f; }
    constexpr float toCelsius() const { return toKelvin() - 273.15f; }
    constexpr float toFahrenheit() const { 
        return (toCelsius() * 9.0f / 5.0f) + 32.0f; 
    }
    
private:
    using PhysicalQuantityBase::PhysicalQuantityBase;
    friend class PhysicalQuantityBase<Temperature, uint16_t>;
};

class Pressure : public PhysicalQuantityBase<Pressure, uint16_t> {
public:
    static constexpr Pressure fromRaw(uint16_t raw) { 
        return Pressure(raw); 
    }
    static constexpr Pressure fromKilopascal(float kPa) {
        return Pressure(uint16_t(kPa));
    }
    static constexpr Pressure fromBar(float bar) {
        return fromKilopascal(bar * 100.0f);
    }
    
    constexpr float toKilopascal() const { return float(value_); }
    constexpr float toBar() const { return value_ / 100.0f; }
    
private:
    using PhysicalQuantityBase::PhysicalQuantityBase;
    friend class PhysicalQuantityBase<Pressure, uint16_t>;
};

// Verwendung in Step:
Temperature measured = sensor->readTemperature();
Temperature target = Temperature::fromCelsius(80.0f);

if (measured >= target) {  // Typsicher!
    // Ziel erreicht
}

// COMPILE-FEHLER (gewollt!):
Pressure p = Pressure::fromBar(2.0f);
auto wrong = measured + p;  // ❌ Compiler-Fehler!
```

================================================================================
METHODE 4: HYBRID-ANSATZ (PRAGMATISCH)
================================================================================

Beschreibung:
- Kombination aus Methode 2 und 3
- Strong Types für Step-Logik (Compile-Zeit-Sicherheit)
- ParameterValue als std::variant für Serialisierung/Storage
- Automatische Conversions zwischen beiden

Code-Beispiel:
```cpp
// Teil 1: Strong Types (wie Methode 3)
class Temperature { /* ... */ };
class Pressure { /* ... */ };

// Teil 2: ParameterValue mit Strong Types
using ParameterValue = std::variant<
    std::monostate,
    bool,
    int32_t,
    std::string,
    Temperature,    // Strong Type!
    Pressure,       // Strong Type!
    Mass,
    Percent
>;

// Teil 3: Automatische Conversions
class Temperature {
    // ...
    
    // Implizite Conversion VON ParameterValue
    Temperature(const ParameterValue& pv) {
        if (auto* t = std::get_if<Temperature>(&pv)) {
            value_ = t->value_;
        } else {
            // Fehlerbehandlung oder Default
            value_ = 0;
        }
    }
    
    // Implizite Conversion ZU ParameterValue
    operator ParameterValue() const {
        return *this;
    }
};

// Teil 4: Typsichere Context-Methoden
class StepContext {
public:
    // Spezifische Getter (kein Variant-Handling nötig!)
    std::optional<Temperature> getTemperatureInput(std::string_view alias);
    std::optional<Pressure> getPressureInput(std::string_view alias);
    
    void writeTemperature(std::string_view alias, Temperature t);
};

// Verwendung in Step - EINFACH & TYPSICHER:
void onActive(StepContext& ctx) override {
    // Einfache Extraktion aus Context
    Temperature measured = ctx.getTemperatureInput("sensor")
                              .value_or(Temperature::fromCelsius(0));
    
    // Einfache Extraktion aus Parameter (automatisch!)
    Temperature target = targetTempParam.value;  // Auto-Conversion!
    
    if (measured >= target) {  // Typsicher!
        ctx.writeTemperature("heater", Temperature::fromCelsius(0));
    }
}
```

PORTABILITÄT ZU ANDEREN EMBEDDED SYSTEMEN
================================================================================

Zielplattformen:
- ESP32-S3 (Xtensa LX7, 32-bit, 512 KB SRAM) - Primär
- ARM Cortex-M4/M7 (32-bit, 128-512 KB RAM) - STM32, Nordic nRF52, etc.
- ARM Cortex-M0+ (32-bit, 16-64 KB RAM) - Low-End MCUs
- RISC-V (RV32I, variabel RAM) - GD32V, SiFive, etc.
- AVR ATmega (8-bit, 2-8 KB RAM) - Arduino-Plattformen

Architektur-spezifische Überlegungen:

┌─────────────────┬─────────────┬─────────────┬─────────────┬─────────────┐
│ Plattform       │ Wortbreite  │ uint16 Perf.│ Template    │ Empfehlung  │
├─────────────────┼─────────────┼─────────────┼─────────────┼─────────────┤
│ ESP32-S3        │   32-bit    │   Gut       │  Exzellent  │  M4         │
│ ARM Cortex-M4   │   32-bit    │   Gut       │  Exzellent  │  M4         │
│ ARM Cortex-M0+  │   32-bit    │   Gut       │  Gut        │  M3/M4      │
│ RISC-V RV32I    │   32-bit    │   Gut       │  Exzellent  │  M4         │
│ AVR ATmega      │   8-bit     │   Langsam   │  Begrenzt   │  M2         │
└─────────────────┴─────────────┴─────────────┴─────────────┴─────────────┘

Wichtige Erkenntnisse:

1. MODERNE 32-BIT MCUs (ESP32, ARM Cortex-M):
   ✅ uint16_t ist effizient (native Register-Größe unterstützt)
   ✅ Template-Metaprogrammierung funktioniert ausgezeichnet
   ✅ Zero-cost abstractions werden optimal compiliert
   → Methode 3 oder 4 ideal

2. LOW-END 32-BIT MCUs (Cortex-M0+, 16-64 KB RAM):
   ✅ uint16_t weiterhin gut
   ⚠️ Templates erhöhen Flash-Nutzung (aber akzeptabel)
   ⚠️ std::variant könnte zu groß sein
   → Methode 3 bevorzugt (ohne Variant), oder Methode 2

3. 8-BIT MCUs (AVR):
   ⚠️ uint16_t Arithmetik ist Multi-Cycle
   ⚠️ Templates können Flash sprengen
   ❌ std::variant zu teuer
   → Nur Methode 2 realistisch

4. PORTABILITÄT-FAKTOREN:
   - Alle Methoden nutzen Standard-C++17 (keine Plattform-spezifischen Features)
   - uint16_t ist auf allen Plattformen verfügbar
   - Templates werden überall unterstützt (Compiler-Qualität variiert)
   - constexpr funktioniert auf modernen Compilern (GCC 7+, Clang 5+)

Empfehlung für MAXIMALE PORTABILITÄT:
→ Methode 3 (Strong Types OHNE std::variant)
→ Bei Bedarf für High-End MCUs: Methode 4 hinzufügen (opt-in)

Design-Prinzipien für Portabilität:
1. Keine dynamische Speicherverwaltung (new/delete)
2. Keine virtuelle Vererbung in kritischen Pfaden
3. constexpr statt Runtime-Berechnungen
4. Header-only wo möglich (einfacher zu portieren)
5. Platform-Abstraction-Layer für Hardware-spezifische Details


================================================================================
HARDWARE-SPEZIFISCHE OPTIMIERUNGEN
================================================================================

ESP32-S3 spezifisch:
- Dual-Core → Parallelisierung möglich
- 512 KB SRAM → Genug für Methode 4 mit std::variant
- FPU vorhanden → Float-Conversions effizient
- L1-Cache (16 KB I-Cache, 32 KB D-Cache) → Profitiert von kompakten Typen

ARM Cortex-M4/M7 spezifisch:
- Single-Precision FPU → Float-Conversions schnell
- Thumb-2 ISA → Kompakter Code
- Tight Coupled Memory → uint16_t Arrays ideal

ARM Cortex-M0+ spezifisch:
- Keine FPU → Float-Conversions langsam (Software-Emulation)
- Begrenzte Register → Einfache Typen bevorzugen
- Kleine Flash → Code-Größe kritisch

Compiler-spezifische Hinweise:
- GCC/G++: Exzellente Template-Optimierung ab Version 9+
- Clang: Beste constexpr-Unterstützung
- MSVC (für Simulation): Gute Unterstützung ab VS2019
- IAR/Keil: Kommerzielle Compiler mit sehr guter Embedded-Optimierung
